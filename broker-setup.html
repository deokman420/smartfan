MQTT broker reference

What the app connects to, why it has to be WebSockets, and what is already running on your Home Assistant host. Short version: nothing needs changing.

✓

No broker configuration is required. The Home Assistant Mosquitto add-on already serves MQTT over WebSocket on port 1884. Verified on 2026-09-27 with a real handshake — the server returned 101 Switching Protocols and negotiated Sec-WebSocket-Protocol: mqtt. The listener 9001 block written into the phase 4 plan is not needed.

Why the app cannot use port 1883

The device talks to the broker over plain TCP on 1883, and so does Home Assistant. The app cannot. A browser has no API for opening a raw TCP socket — not for security theatre reasons, but because the sandbox simply does not expose one. Everything a page can open is HTTP, WebSocket, WebRTC or WebTransport.

MQTT solves this with a defined WebSocket binding: the same MQTT packets, framed inside WebSocket messages, with the subprotocol negotiated as mqtt during the handshake. It is the same protocol and the same broker, reached through a door the browser is allowed to use.

This is why the app is a client of the broker, not of the device. There is no server in between, which is what makes “local first” literal. It also means that if the broker is down the app goes stale while the fan keeps running on its own logic — the app is never in the control path.

What is actually listening

Probed directly on 192.168.0.5:

PortStateProtocolUsed by
1883 open MQTT over TCP The Pico, Home Assistant, ota_publish.py
1884 open MQTT over WebSocket The app. Confirmed to negotiate mqtt
8883 closed MQTT over TLS Not enabled
8884 closed MQTT over WebSocket + TLS Not enabled
9001 closed — The conventional Mosquitto WebSocket port. The add-on uses 1884 instead, so nothing needs to be added here

1883 and 1884 are the add-on’s defaults. You had already enabled them; they were simply never confirmed from the app’s side.

Verify it yourself

The port being open proves a socket is bound. It does not prove the thing behind it speaks MQTT. This does:

python - <<'EOF'
import base64, os, socket
key = base64.b64encode(os.urandom(16)).decode()
s = socket.create_connection(("192.168.0.5", 1884), timeout=6)
s.sendall((
    "GET / HTTP/1.1\r\nHost: 192.168.0.5:1884\r\n"
    "Upgrade: websocket\r\nConnection: Upgrade\r\n"
    "Sec-WebSocket-Key: %s\r\nSec-WebSocket-Version: 13\r\n"
    "Sec-WebSocket-Protocol: mqtt\r\n\r\n" % key).encode())
print(s.recv(512).decode())
EOF

A healthy broker answers:

HTTP/1.1 101 Switching Protocols
Upgrade: WebSocket
Connection: Upgrade
Sec-WebSocket-Accept: …
Sec-WebSocket-Protocol: mqtt

The last line is the one that matters. A 101 without mqtt means something is listening but it is not an MQTT broker, and a client would connect and then hang.

Authentication

The add-on accepts Home Assistant user accounts as broker logins, and also its own logins: list in the add-on configuration. Phase 2 settled on one broker account per device so a single misbehaving or compromised device can be revoked without touching the others.

That principle extends to the app, which gets its own account rather than reusing the device’s:

WhoAccountWhy separate
The Pico pico-fan-bathroom Publishes telemetry, subscribes to its own command topic
Home Assistant its own Discovery and state
The app to be created Read-mostly. Revoking it must never take the fan offline

Credentials reach the browser. Anything the app connects with is readable by anyone who opens the page and its dev tools — that is true of every browser MQTT client and cannot be engineered away. Give the app account the narrowest ACL that still works, and treat it as a LAN credential, not a secret.

Topic map

The app subscribes to what the device already publishes. Nothing new is added on the firmware side.

TopicDirectionCarries
fan/bathroom/state device → app The full telemetry payload, every 30 s and on change
fan/bathroom/status device → app Retained availability, plus the last will on an ungraceful drop
fan/bathroom/cmd app → device Commands, including update <url> for OTA
homeassistant/…/config device → broker Retained discovery. The app can read it to learn the entity set rather than hardcoding one

The room segment is deliberate. Multi-room topics were chosen in phase 2 “while it is cheap”, so a second unit is fan/<room>/… with no restructuring.

If you ever do need to change it

Nothing below is required today. It is here so the next person does not have to rediscover where the knobs are.

Custom Mosquitto configuration

The add-on reads extra config from /share/mosquitto/ when told to. In the add-on’s configuration:

customize:
  active: true
  folder: mosquitto

Then a file such as /share/mosquitto/extra.conf is included at startup. That is where an additional listener, per-topic ACLs or tuning would go. Restart the add-on for it to take effect.

TLS

8883 and 8884 are closed. On a home LAN, with the app, the broker and the device all on the same network, that is a defensible position rather than an oversight. It stops being defensible the moment any of the three is reachable from outside the LAN — at which point the app needs wss:// on 8884, and a certificate the browser will accept, which is the genuinely awkward part on a private address.

Websocket path

Mosquitto serves the WebSocket at the root path. The app connects to ws://192.168.0.5:1884/. A client that defaults to /mqtt — several do — will fail the handshake and report it as a connection refusal, which sends you looking at the firewall instead of the path.

Troubleshooting

SymptomMost likely cause
Connects, then closes immediately Bad credentials. Mosquitto accepts the socket, rejects CONNECT, then disconnects — from the browser it looks like an unstable network
101 but no MQTT ever flows Subprotocol not negotiated. The client must ask for mqtt in the handshake
Handshake fails outright Wrong path. Try / rather than /mqtt
Works on the desktop, not the phone Phone on guest Wi-Fi or cellular. The broker is LAN only by design
Page served over HTTPS cannot reach ws:// Mixed content. Browsers block insecure sockets from secure pages. Serve the app over plain HTTP on the LAN, or move the broker to wss://
Two clients keep kicking each other off Shared client ID. Each connection needs a unique one — this looks exactly like a flaky network
